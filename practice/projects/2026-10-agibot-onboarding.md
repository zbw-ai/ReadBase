## 2. 公司与业务：理解需求从哪里来

<a id="company"></a>
### 2.1 公司背景：读战略时要翻译成工程问题

截至本次核查，智元官网覆盖远征、灵犀、精灵等机器人产品，以及模型、数据、开发平台和场景解决方案。它不是只有一款 VLA，也不是只有硬件产品。[官网](https://www.agibot.com.cn/)

邓泰华在 2026 年 4 月的合作伙伴大会上，将路线描述为本体与运动、交互、作业智能协同，强调模型投入、平台复用和从开发验证走向持续部署。演讲还提出通过真实部署积累数据、继续改进模型。**这些是公司公开战略，不是对内部平台成熟度的独立验证。** [官方演讲全文，5 月 7 日发布](https://www.agibot.com.cn/article/315/detail/154.html)

对当前岗位，更重要的不是背融资名单，而是形成三个待验证的问题：

1. 公司模型投入，具体转化成了哪些团队、训练任务和交付日期？
2. 多条业务线需要的共性能力是什么，哪些差异必须保留？
3. 从数据、实验到可部署模型，现在哪里最拖慢迭代，谁对这段链路负责？

**我的入职判断**：中央研发岗位的潜在价值，是把重复遇到的问题解决成可复用能力，而不是只为每个业务写一份脚本。但这只是岗位假设；若智算业务部的近期重点是算力服务、异构适配或交互推理，计划要跟着实际任务调整。

| Genie Envisioner / GE-Sim 2.0 | 世界模型方向；GE-Sim 2.0 提供动作条件下的闭环视频模拟路径，不是 Genie Sim 的另一种拼写；[官方仓库](https://github.com/AgibotTech/GE-Sim-V2) | 用于研究、评估还是策略训练？可用组件和完整系统有什么差距？不把生成视频质量等同控制有效性 |

## 3. 岗位定位：从性能调优走向一段系统的技术负责

<a id="role"></a>
### 3.1 这次角色升级，升级在哪里

建议把“专家”的要求理解为四个可观察动作，而不是职级称谓：

1. **定义问题**：把“训练慢”“卡不够”“模型不好用”拆成可测量的瓶颈，说明业务损失和处理优先级。
2. **做出取舍**：给出现有栈内改进、局部替换、较大改造的成本与风险，不把最熟悉的框架当成默认答案。
3. **推进闭环**：自己承担关键分析和实现，明确跨团队依赖；遇到资源或优先级冲突及时向 +1 提供决策选项。
4. **留下可用能力**：代码进入维护主线，有测试、观测、文档、回滚和接手人；不是只有一个 benchmark 截图。

这不等于入职就管理团队，也不等于要包办数据、算法、平台和机器人控制。**先争取一个明确的技术责任范围，再逐步扩大影响。**

### 3.2 原有经验怎么迁移，哪些需要补

| 已有积累 | 可以直接复用的方法 | 在具身场景要补的判断 |
|---|---|---|
| 大模型适配与性能交付 | 跑通基线、profile 归因、配置与算子对照、跨团队解决问题 | 真实 workload 可能先受视频 I/O、冻结模块或小算子开销限制，不一定需要复杂模型并行 |
| Megatron / SFT / 长上下文 | 显存账本、并行通信、重计算、数据等待分析 | 熟悉 PyTorch FSDP2；同时保留单卡／DDP 选项，按实际内存与吞吐选择 |
| verl / AReaL / Gateway | 异步供需、背压、超时、版本与轨迹归属 | 机器人动作有时限和物理后果，旧请求不能盲目重试；仿真 RL 与真机控制也不能混为一谈 |
| 正确性与模型产物交付 | loss、mask、状态恢复、工件版本、可追溯实验 | 增加相机／state／action 对齐、单位与坐标系、归一化、任务评估和安全边界 |

**不需要伪装成具身算法专家。** 可以直接说：“训练和后训练系统的方法我比较熟，机器人动作语义和闭环评估是我入职后重点补齐的部分。我会先跟一条真实任务把数据、模型和执行链路走通。”

<a id="interfaces"></a>
### 3.3 第一周建立一张协作接口表

下表是访谈对象建议，不是已确认的组织分工。请由 +1 引荐具体负责人，每次约 20–30 分钟，先听最近一次实际案例。

| 对象 | 重点问什么 | 双方需要确认的接口 |
|---|---|---|
| 算法／模型负责人 | 最近一次实验最耗时在哪？如何判断模型变好了？ | 模型入口、冻结范围、loss、有效 batch、正确性与效果验收 |
| 数据负责人 | 原始采集到可训练数据经过哪些步骤？版本如何追踪？ | schema、采样与 split、时序对齐、质量检查、访问权限 |
| 算力／平台／存储负责人 | 配额、排队、互联、共享限制、故障和成本如何管理？ | 资源申请、环境、监控、SLO、生产值守与升级路径 |
| 推理／部署负责人 | 哪段端到端时延最敏感？模型如何灰度和回滚？ | 模型＋processor＋normalization＋adapter 的版本契约 |
| 仿真／评测／控制负责人 | 离线、仿真和真机分别如何验收？实验安全要求是什么？ | 场景版本、成功判据、失败分母、权限、急停与安全负责人 |

每次访谈记下：**一件当前痛点、一个证据入口、一名负责人、一个后续动作**。不要第一次见面就评价旧架构“不先进”；先问它解决过什么约束。

如果多个团队都让自己“顺手帮一下”，记录影响和工作量，由 +1 确认优先级。支持业务是职责的一部分，但持续支援也需要有范围和归属。

## 4. 和 +1 沟通：第一次就把成功标准谈具体

<a id="first-one-on-one"></a>
### 4.1 入职前可以发的消息

> 孟总，我周一入职，上海这段时间也想尽快和团队把协作建立起来。想在入职后约您 30–45 分钟，主要对齐智算业务部近期最重要的业务、您希望我承担的范围，以及试用期交付标准。我会先了解现有链路和瓶颈，带着一个初步计划讨论，再按团队优先级收敛。

称呼沿用双方原有习惯即可。不需要发送长篇技术方案，也不用在报到前主动承诺某个提升比例。

### 4.2 首次 1:1：45 分钟建议议程

| 时间 | 要讨论的内容 | 希望留下的结论 |
|---|---|---|
| 0–5 分钟 | 简述自己的能力与这次希望承担的责任 | 你能立即贡献什么，哪些领域需要学习 |
| 5–15 分钟 | 业务部近期重点和最急的问题 | 主要服务对象、前三项工作、硬性业务时间点 |
| 15–25 分钟 | 岗位职责、现有团队和决策权限 | 独立负责范围、合作人、已有 owner、资源申请与拍板人 |
| 25–35 分钟 | 试用期成果与验收 | 1 条主线、阶段交付、验收人、正式考核流程 |
| 35–45 分钟 | 协作节奏、上海安排与下一步 | 每周同步方式、首周引荐名单、两周后目标确认时间 |

**开场可以直接说：**

> 我之前积累比较多的是模型适配、训练性能和后训练系统，习惯先建立基线，再定位瓶颈并验证效果。这次我想在一段明确的链路上承担从问题定义到交付的责任。入职前能了解到的是公开产品，内部情况还不了解，所以我先想听您说：现在最希望这个岗位解决哪一个问题？三个月后，您看到什么结果会认为这次招聘达到了预期？

### 4.3 六个必须问清的问题

1. **服务谁**：“智算业务部目前主要面向哪些团队？训练引擎、算力平台、数据链路和推理服务，哪些是我们的主责？”
2. **先做什么**：“近期最影响业务迭代的是哪三件事？如果我这三个月只能做成一件，您最希望是哪件？”
3. **负责到哪里**：“希望我独立负责哪个模块？技术方案、代码合入和生产变更分别由谁评审？是否预期带项目或带人？”
4. **怎样算做成**：“交付要到实验验证、业务试用还是正式运行？谁验收？性能、稳定性、模型效果和文档分别有什么要求？”
5. **资源和依赖**：“现有同事中谁熟悉这条链路？有哪些可用算力、测试环境和评测资源？跨团队依赖遇到冲突怎么协调？”
6. **如何持续对齐**：“我们每周固定同步还是按项目节点同步？正式转正评审什么时候、谁参与？上海阶段结束后如何衔接工作地点和团队协作？”

最后再问一句：“这个岗位最容易做偏的地方是什么？您希望我避免哪些做法？”它能帮助了解真实期待，而不是猜领导喜欢什么。

### 4.4 几种常见回答，怎么接

| +1 的回应 | 建议接法 |
|---|---|
| “先熟悉一下，哪里都需要人” | “我先用一到两周梳理主要 workload 和痛点，形成三个候选，再请您选定一条主线。这样熟悉也会有明确产出。” |
| “希望你把训练效率提起来” | “我先确认哪个模型和训练阶段、当前基线及业务目标。再拆数据等待、计算和通信，提出能验证的改进范围。” |
| “先把某个紧急项目交付” | “可以，我先确认截止时间、验收人和必须保住的质量底线；同时和您对齐原计划哪些延后，交付后再提炼可复用部分。” |
| “搭一套统一平台” | “我建议先选一个真实用户和完整路径，确认现有平台能复用哪些；先解决最关键断点，再评估统一到哪一层。” |
| “要兼顾 NVIDIA 和昇腾” | “我先选代表性 workload，明确两边的功能、数值、性能、运维验收矩阵，再决定共用抽象和需要独立优化的部分。” |

不要用“我都可以”结束对话。接受挑战后补齐范围、资源、依赖和验收，比泛泛表达信心更有帮助。

<a id="alignment-note"></a>
### 4.5 会后发一段确认，避免各自理解不同

> 今天沟通后，我的理解是：前三个月优先解决【业务问题】，主要服务【团队／场景】，我负责到【边界】。前两周先完成【基线和诊断】，再共同确认量化目标；阶段验收由【负责人】参与。暂不开展【非目标】，依赖【资源／合作人】。我们按【节奏】同步，出现范围或资源变化时重新确认。若理解有偏差，麻烦您指出，我据此调整计划。

这段内容应发送并保存在公司批准的沟通系统中，不直接贴回公开仓库。

### 4.6 和 +2 及前同事怎么相处

- **+2 沟通讲业务结果和系统取舍**：解决哪个瓶颈、对哪些模型／团队有用、投入多少、还缺什么决策；技术细节作为可展开的证据。日常优先级仍与 +1 对齐，不形成两个互相冲突的任务清单。
- **前同事关系用于快速理解背景**，但不默认已经获得信任、权限或共同立场。主动认识算法、数据和部署同事，不能只在熟悉的圈子里沟通。
- **有分歧先给证据和备选方案**：“A 交付快但覆盖窄，B 复用更多但多依赖两个团队，我建议这期 A、下期验证 B。”不要把个人技术偏好包装成唯一正确架构。
- **不能完成时尽早说清楚**：当前证据、阻塞影响、已尝试路径、需要谁在何时做决定。既不隐瞒风险，也不把跨团队问题简单归咎别人。

## 5. 三个月计划：一条主线，分阶段验收

<a id="ninety-days"></a>
### 5.1 时间线与成果

以下按 2026-10-26 为 Day 1 规划。30／60／90 天是复盘节点，**不等同于合同中的三个月**；正式试用期终止日、评审日和提交材料时限以 HR／合同确认结果为准。90 天节点约为 2027-01-23，正式评审应提前安排。

| 阶段 | 重点动作 | 交付物 | 建议验收方式 |
|---|---|---|---|
| 首周，10/26–10/30 | 确认目标、协作人和访问权限；看一条真实业务链路 | 目标草案、系统与接口图、未知项清单 | 和 +1 确认“当前理解是否正确”，不把拿到权限当作技术成果 |
| 首月，至 Day 30（11/24） | 跑通获批代表 workload；建基线、定位主要瓶颈、选主线 | 可复现基线、profile 证据、一个低风险先行改进、目标确认表 | 算法／平台同事能复跑；+1 确认主线、非目标与资源 |
| 第二月，至 Day 60（12/24） | 实现主线，做单变量验证、质量回归和小范围试用 | 评审通过的实现、对照报告、试用反馈 | 指标变化能够解释，质量护栏未破坏，至少一个真实使用方参与验收 |
| 第 9–12 周，1 月中旬前 | 收敛边界、稳定性观察、文档和交接；提前准备评审 | 试用／发布记录、runbook、回滚与恢复路径、成果总结 | 团队能独立使用或维护；观察窗口由业务方约定，不预填“长期稳定” |
| 正式评审前 | 对照原目标说明结果、差距与后续 | 一页总结和必要证据，下一阶段建议 | 由约定的评审人与流程确认，不以本文作为通过承诺 |

每两周复核一次任务排序。资源、业务或算法路线变化时，记录目标如何调整，避免仍按已失效的原计划解释结果。

<a id="first-week"></a>
### 5.2 首周每天做什么

| 日期 | 主要动作 | 当天留下什么 |
|---|---|---|
| 周一 10/26 | 报到、设备与权限；+1 沟通；认识直接协作同事 | 待确认事项、系统入口、第一版目标和协作名单 |
| 周二 10/27 | 跟算法同事看一个模型：任务、样本、loss、评估与发布 | 一页“输入 → 样本 → 模型 → 产物 → 验收”说明 |
| 周三 10/28 | 跟平台同事看一次任务从提交到运行；看历史故障和监控 | 资源、数据、执行、checkpoint、日志的链路图及 owner |
| 周四 10/29 | 在权限和资源就绪后运行一个小规模参考任务；否则先读日志／回放 | 第一份测量记录或缺失条件清单，不为赶进度私用资源 |
| 周五 10/30 | 和主要用户确认理解，给 +1 汇报事实、假设和候选主线 | 首周一页小结；下一周验证计划、所需资源和约定时间 |

不要求首周就提出组织级架构重构。若入口复杂、权限未就绪，及时说明，不通过绕过审批制造“跑通”的假象。

<a id="candidate-projects"></a>
### 5.3 三条候选主线：只选一条作为试用期核心

默认从最熟悉的训练链路切入，但最终由业务优先级和测量决定。先行改进也应服务主线，不另开一个大项目。

#### A. 代表性模型的有效训练效率

- **适合**：业务最急的是实验慢、卡利用不足或多模态数据供给不稳。
- **最小范围**：一个模型版本、一个数据版本、一个常用训练任务；先建立稳定基线。
- **怎么做**：分解取数、解码、增强、collate、H2D、前后向、通信和保存；只针对主要瓶颈做改动。必要时比较 DDP/FSDP2、分片粒度、microbatch 和重计算，而不是预先决定换框架。
- **先行改进示例**：补齐可复跑 profile 入口；修一个已验证的数据等待或显存问题。是否能提速由实测决定。
- **交付**：一个被业务采用的配置／实现、对照报告、数据与数值回归、使用说明。
- **不做**：同时改模型结构、数据分布和多种并行配置后，把所有收益归给自己的一处改动；三个月统一所有训练栈。

#### B. 训练恢复与实验可追溯

- **适合**：训练频繁中断、恢复依赖人工、结果难复现，失败损失比单步耗时更严重。
- **最小范围**：一条高价值训练路径，先支持相同拓扑恢复，再按业务必要性考虑 reshard。
- **怎么做**：梳理模型、optimizer、scheduler、RNG、数据进度和预处理版本；验证保存完成点、恢复语义、checkpoint 到评估产物的关联。
- **先行改进示例**：补一个恢复验收测试和标准 runbook，缩短重复排查。
- **交付**：获批环境中的恢复演练、状态缺口修复、监控与操作说明；用损失训练量、恢复时间和人工介入衡量。
- **不做**：未经批准中断生产任务、下线节点或制造网络故障；只证明权重能加载就声称完整可恢复。

#### C. 模型推理链路的时延与版本可靠性

- **适合**：业务最急的是交互体验、策略响应或部署稳定性，而不是训练吞吐。
- **最小范围**：一条模型服务，用获批数据回放／仿真先建立端到端时间线。
- **怎么做**：区分排队、预处理、模型执行、后处理、网络与消费时间；核输入时间戳、模型和处理器版本，按瓶颈验证 batching、compile、CUDA Graph 或缓存。动作模型额外核输入新鲜度、chunk 消费和过期响应。
- **先行改进示例**：补齐关联 ID 与 p95/p99 指标，找到并修复一段可定位的等待或错误重试。
- **交付**：离线／仿真对照、服务质量回归、超时／取消／回滚方案；若涉及真机，再走专门审批和安全流程。
- **不做**：把 token 吞吐直接当作机器人收益；未经授权替换真实机器人策略或取消控制层保护。

**两周后怎么选**：比较业务收益、证据是否充分、能否在期限内验证、是否已有 owner、资源依赖和质量风险。优先选“有真实用户、能测量、边界可控”的问题，而不是最热门的技术名词。若异构适配是主管首要任务，可将其嵌入 A 或 C，但必须缩小为明确的模型与硬件组合。

<a id="acceptance"></a>
### 5.4 目标怎么写，才不会既虚又过度承诺

推荐句式：

> 在【固定模型／数据／硬件／软件版本】上，解决【已证实的瓶颈】，将【主指标】从【基线】改善到【商定目标】，同时满足【质量护栏】，由【业务使用方＋技术评审人】在【日期／观察窗口】验收，并交付【可维护产物】。

入职前不填“提升 30%”或“成本减半”。先在两周内核实基线、可实现范围和统计口径，再与 +1 商定目标；如果基线尚不可信，第一项交付就是测量与正确性基础。

| 维度 | 推荐观察方式 | 容易误读的地方 |
|---|---|---|
| 业务迭代 | 从一个明确需求进入队列，到拿到可评估产物的时间；分开排队、准备、运行、评估 | 单步更快，不代表排队和人工等待减少 |
| 训练效率 | 固定 workload 下，有效样本／帧／token 的端到端吞吐；另报稳态 step 均值与尾部、数据等待、峰值显存 | 不能把不同分辨率、时间窗、冻结范围和有效 batch 混为一组结果；按场景选择单位 |
| 资源成本 | 总分配 accelerator-hours ÷ 有效完成的训练量或合格实验数；标注计量边界 | 不跨异构卡型直接比较原始卡时；GPU busy 或 MFU 不是业务目标的替代品 |
| 稳定性 | 完成率、失败原因、损失步骤、恢复时间和人工介入；记录分母及观察窗口 | 三次成功不能推出长期 SLA；样本不足时报告逐次结果 |
| 推理与执行 | p50/p95/p99、超时率和有效吞吐；动作场景增加观测新鲜度与 deadline miss | 模型 forward、服务响应、动作执行是不同边界，不相互替代 |
| 正确性与质量 | 数据身份、时间对齐、mask、数值、恢复状态；算法方确认效果与评估协议 | 性能提升不能通过丢样本、降任务难度、改变 loss 或放宽质量门槛获得 |
| 可复用性 | 一名非作者可按文档复跑／接手，有测试、观测、回滚与维护责任人 | 合入代码不等于用户已用；用户已用不等于全场景推广 |

比较时固定关键变量，单项消融与完整 recipe 对照分开；记录 warmup、重复次数、缓存状态、失败样本和测量开销。业务质量容差应在实验前商定，不能看完结果再修改门槛。

## 6. 技术准备：围绕实际任务学习，不再堆框架名单

<a id="technical-prep"></a>
### 6.1 入职前 3–4 小时的最小准备

| 时间建议 | 做什么 | 读完能说清什么 |
|---|---|---|
| 30–40 分钟 | 本页[公司地图](#business-map)与[+1 提纲](#first-one-on-one) | 公司有哪些不同业务，哪些内部事实还不知道 |
| 45–60 分钟 | [具身模型：样本到 loss 与动作](../../05-embodied-infra/topics/embodied_models_primer.md#sample-to-action) | observation、state、action、action chunk、BC 与 RL 的区别；MLLM 不是 vLLM |
| 45–60 分钟 | [多模态数据 I/O](../../05-embodied-infra/topics/embodied_data_io.md) | episode、时间戳、采样窗口、视频解码、归一化与 mask 如何影响正确性和速度 |
| 45–60 分钟 | [FSDP/FSDP2/ZeRO](../../02-training-infra/topics/fsdp.md) | 参数、梯度、optimizer、activation 各占多少；什么时候 DDP 足够，什么时候值得分片 |
| 20 分钟 | 写一页自己的未知项和第一周问题 | 能向算法、数据、平台同事提出具体问题，而不是泛泛求介绍 |

若时间不足，优先“一个样本如何变成动作”与 +1 沟通提纲。代码和性能优化可以沿真实任务继续深入。

### 6.2 入职后随任务展开的四个技术模块

**数据与学习契约**：拿一条样本，从原始 episode 追到 batch。确认相机帧和 state/action 的相对时刻、动作坐标与单位、有效长度、训练／验证 split 和归一化统计。先证明拿对数据，再讨论多 worker、缓存和预取。[正文](../../05-embodied-infra/topics/embodied_data_io.md)

**训练与资源**：先看可训练模块、图像数量／分辨率、时间窗与 activation，再算状态分片价值。FSDP2 不是因“具身模型小”就默认使用，Megatron 也不是因为熟悉就默认使用。硬件、框架版本和规模待入职核对；旧岗位曾可用的 A100 资源不视为新岗位授权。[训练选读](../../02-training-infra/README.md#original-library) · [FSDP](../../02-training-infra/topics/fsdp.md)

**推理与执行**：交互服务关注响应和会话；动作策略还要关注何时观察、何时执行、过期结果如何处理。CUDA Graph 主要减少合适场景的提交开销，不等于自动融合全部算子或消除 HBM 流量；缓存也必须满足输入及版本复用条件。[推理路线](../../03-inference-infra/roadmap.md) · [状态边界](../../03-inference-infra/topics/inference_state.md)

**RL、仿真与评测**：只有确认存在交互学习需求时再深入 rollout 与 trainer。先问环境 reset、成功判据、reward、终止／截断、策略版本和数据是否丢弃。LLM Agent 的工具返回不等于物理动作可以安全重放；仿真结果也不自动代表真机。[RL 路线](../../04-rl-infra/roadmap.md) · [具身评估与部署](../../05-embodied-infra/roadmap.md#stage-5)

### 6.3 怎样学习才算形成能力

围绕现役模型做五张小纸面说明即可：输入输出；模块与参数／activation；数据时间线；训练和推理耗时；评估与版本。每张都能指向一个实际样本或任务，不需要先写长篇综述。

已有 [A100 实验 E00–E08](../experiments/a100_fsdp_io_lab.md)可复用为实验设计参考，**全部仍是未执行计划**。在新公司使用前重新确认硬件、版本、数据许可、预算与访问授权；不直接照抄卡数和命令发起作业。

“本人已读懂”“公开代码可运行”“业务试用过”“正式上线”分别记录，不能互相替代。

## 7. 试用期上海出差：让现场协作有明确用途

<a id="shanghai"></a>
### 7.1 到上海是为了尽快理解系统与建立协作

建议把现场阶段用于四件事：跟算法人员看真实实验、跟平台人员看任务和故障、跟评测／部署人员看一次完整验收、把关键合作接口建立起来。坐在同一办公室本身不是成果，也不应靠持续延长工时替代优先级管理。

| 需确认的事项 | 向谁确认 | 问到什么程度 |
|---|---|---|
| 报到与办公点 | HR／行政／+1 | 具体楼宇、接待、首周安排；官网列有多个地点，不自行猜测 |
| 差旅属性与时间 | HR／+1 | 连续驻沪还是阶段往返；审批起止日与变更流程；试用期与出差是否同步结束 |
| 住宿与往返 | 行政／HR | 由谁预订、标准、支付与票据、退改、往返频率如何审批 |
| 设备与网络 | IT／平台团队 | 电脑、账号、远程访问、数据下载、录屏及 AI 工具使用规范 |
| 工作与支持节奏 | +1／项目负责人 | 例会、发布／值守安排、紧急联系、休息与交接方式，以公司制度为准 |
| 上海阶段后的衔接 | +1／HR | 长期工作地点、协作者分布、异地协作和后续出差预期；不要等最后一周才问 |

可直接说：

> 上海现场阶段我会重点把业务链路和协作关系建立好。也想提前对齐阶段结束后的工作地点、交接和协作方式，方便我安排工作与生活。我们是否可以在第一个月末确认一次，第三个月前再落实具体安排？

### 7.2 入职期间的安全与信息边界

- 公开学习资料可以继续在本仓库整理，但公司内部信息只进入批准的内部工具。使用 AI、外部 profiler 服务或云端文档前，核对公司的数据与工具政策。
- 不用前公司账号或算力继续跑实验，不携带前雇主敏感材料；通用经验与受限制的实现、数据要分开。
- 不擅自重置共享设备、清共享缓存、压测存储、变更网络或注入生产故障；先有明确范围、时间和批准。
- 真实机器人不是普通测试客户端。策略替换、运动和现场测试需要产品流程、场地许可、安全负责人和保护措施；先用回放／仿真，不能通过取消限位或安全保护来取得性能结果。
- 公开项目的许可证、数据使用限制及依赖也需要核对；可下载不代表可以直接用于公司的商业训练。

## 8. 持续工作模板：用事实支撑周报和转正

### 8.1 两周内确认的一页目标表

下列空表供在内部填写。本版没有填好的业务目标、内部结论或验收承诺。

| 字段 | 应填写的内容 |
|---|---|
| 业务问题与使用方 | 谁被什么问题阻塞，为什么此时值得优先做 |
| 责任与非目标 | 自己负责到哪，哪些交由其他 owner，哪些明确不在本期做 |
| 基线 | workload、版本、环境、指标、统计窗口和证据位置 |
| 成果与目标 | 主指标、正确性／质量护栏、交付物，尚未测量的项标待确认 |
| 协作者与资源 | 技术接口人、评审人、验收人、资源审批人及依赖日期 |
| 节点 | 基线确认、方案评审、试用、观察、最终验收时间 |
| 风险与退路 | 不成立时如何停止、缩范围或切换方案；回滚办法 |
| 目标确认记录 | 与 +1 确认日期、变更记录；不把沉默当同意 |

<a id="weekly-update"></a>
### 8.2 周报：五段就够

> **本周结果**：完成了什么可验证结果，对哪个使用方有什么影响。
>
> **证据**：配置／代码版本、对照范围、测量或回归链接；区分事实和推测。
>
> **风险**：什么会影响日期或质量，已经尝试了什么。
>
> **需要决策**：请谁在什么时候决定什么；给出推荐方案和备选。
>
> **下周交付**：一到两项具体产物，写清验收方式。

示例仅示范表达，不代表已发生：

> 这周已建立目标模型的训练基线，并把等待拆成了取数、解码和 H2D。当前证据指向解码长尾，但还不能认定是唯一瓶颈。下周准备在固定采样语义下做并发度和预取的独立对照。需要平台同事确认测试时段和资源上限；如果无法隔离共享干扰，会先交付离线解码对照，并明确端到端结论的限制。

### 8.3 技术方案：正文先控制在两页

按这个顺序写：问题与业务影响 → 当前基线 → 两到三个方案及取舍 → 推荐方案与非目标 → 实施及依赖 → 正确性与效果回归 → 发布／回滚 → 验收与维护人。

先讲为什么值得做，再讲为什么选择这条路。需要大量 trace、配置或源码时放附件，不让决策者先阅读十页细节才能找到结论。

<a id="risks"></a>
### 8.4 风险与目标变化怎么处理

| 看到的信号 | 应对动作 |
|---|---|
| 两周后仍说不清自己的主线和验收人 | 带三个候选及取舍请 +1 确认；必要时把“完成现状诊断”作为阶段目标，而不是无限期熟悉 |
| 每天临时支持，主线持续延期 | 汇总支持耗时与影响，请 +1 重排优先级；不私下承担所有截止日期 |
| 没有稳定基线，却要求立刻报提升百分比 | 先列缺失的变量与数据；承诺基线确认日期，不编造收益 |
| 指标变好但模型效果／行为变差 | 停止推广，检查数据、数值、时间与版本语义，优先回退到已验收路径 |
| 实现完成但没人使用 | 尽早引入真实使用方共同试用，确认接入、文档、评审或需求本身的问题 |
| 跨团队依赖迟迟没有负责人 | 说明影响、最晚决策时间与可行降级方案，请 +1 协调，而不是只在周报写“等待” |
| 第三个月仍未明确转正流程 | 主动与 +1／HR 确认评审时间、材料与参与人；不要到最后一天才发现缺项 |

这些是风险观察项，不是对当前团队已有问题的判断。

<a id="probation-review"></a>
### 8.5 转正材料从第一周积累，评审前再汇总

建议准备六页左右，按公司实际格式调整：

1. **职责与原目标**：当初要解决什么，期间有哪些经确认的变化。
2. **问题与基线**：业务影响、系统边界、原始证据。
3. **关键技术判断**：为什么选这个方案，排除了什么，自己亲自完成哪部分。
4. **结果与质量**：固定口径的前后对照、回归、使用方反馈；没有足够证据的地方明确说明。
5. **可复用交付**：进入哪个维护路径，谁在用，测试／监控／runbook／回滚是否齐全。
6. **不足与下一阶段**：剩余限制、需要补的能力、下一项最值得做的事及资源条件。

成果材料区分个人贡献、团队共同工作和开源原生能力。若优化被证伪，也可以交付可靠基线、排除的路径与节省的试错，但应及时与 +1 重定目标，不在最后一刻将未达成目标重新包装成成功。

### 8.6 当前待办与后续维护

- [ ] HR 确认报到、试用期正式起止和评审流程。
- [ ] +1 确认岗位主责、近期业务、协作名单与同步节奏。
- [ ] 首周了解一条真实链路，区分已确认事实与待验证假设。
- [ ] 两周内商定一条试用期主线、基线确认日期和验收人。
- [ ] 第一个月末复核上海阶段后的衔接安排。
- [ ] 第三个月前确认评审时间，按证据整理成果。
