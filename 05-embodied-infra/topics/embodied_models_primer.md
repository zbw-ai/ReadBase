# 具身模型入门：从理解杯子到输出动作

[核心入口](embodied_infra.md) · [所属 Part](../README.md) · [六阶段路线](../roadmap.md#stage-1)

这篇先解释模型在解决什么问题，再把它接到 Infra。贯穿例子是“把桌上的杯子递给我”；例子包含指代澄清、抓取和失败恢复，但不代表某个公开模型已经可靠实现全部过程。本文以机器人操作为主。

**快速认识**：VLM 提供视觉语言理解；VLA 根据观察与目标生成动作；如果 VLT 指 Vision-Language-Task，则偏向高层任务决策。Infra 要保证数据语义正确、训练供给有效、动作及时、版本一致，并用闭环任务结果验收。先读[缩写与分工](#model-roles)，再读[岗位核心关注点](#infra-priorities)。

读完速查后，按问题深入：[动作怎样生成、计算花在哪里](#action-compute) → [一个样本怎样走到 loss 与执行](#sample-to-action) → [BC／RL 怎样改变系统](#bc-rl-infra)。每次只需选一条路径，最后用[掌握检查](#mastery)确认能否解释。

<a id="map"></a>
## 1. 问题与概念地图

机器人看到的是 observation，不是完整世界状态：相机可能看不见杯柄，关节编码器不能直接说明杯子是否滑动。Policy 根据可用信息选动作，controller 将目标变成符合硬件接口的执行；执行改变环境，下一次观察再检验结果。

<a id="model-roles"></a>
### VLM、VLT、VLA：先看输入输出与职责

**VLT 需要先确认出处。** 小鹏 IRON 的官方披露使用 Vision-Language-Task，将其定位为自主决策模块；这可以帮助理解任务层，但不是统一的行业模型分类。[2025 ESG 报告](https://www.sec.gov/Archives/edgar/data/1810997/000119312526160201/d134229dex993.htm)（2026-04-16 发布，印刷页 60）与[官方产品页](https://www.xpeng.com/technology/ai_robot_iron)只支持这里的名称与角色说明，不能据此推断具体网络、训练目标、模块接口或实测能力。其他文章中的 VLT 应按原文定义解释；[来源与证据边界](../../research/tracking/backfill/2026-04.md#xpeng-vlt-terminology)。

| 名称与全称 | 典型输入与问题 | 可能的输出 | 理解边界 |
|---|---|---|---|
| **VLM：Vision-Language Model，视觉语言模型** | 图像、模型支持的视频与语言，理解场景和指令 | 视觉语言表征、描述、回答、澄清或任务状态 | MLLM 是多模态大语言模型，可能支持更多模态；能回答不等于能控制；也不要与 vLLM 推理引擎混淆 |
| **VLT：Vision-Language-Task，视觉语言任务模型（此处按 IRON 语境）** | 结合场景与目标，决定下一步做什么任务 | 可用子目标、任务步骤或技能选择理解其职责；这是教学抽象，非已公开接口 | 任务规划可由 VLM 等实现；VLT 名称本身不能证明自主性或规划可靠性 |
| **VLA：Vision-Language-Action，视觉语言动作模型** | 图像、语言指令，以及具体模型支持的本体状态／历史，预测如何行动 | 动作 token 解码后的数值、连续向量或动作段 | VLA 不限定唯一训练算法；policy 是更广的策略概念，不一定有语言输入 |
| Planner | 选择子任务或候选行动 | 子目标、计划、轨迹 | 不要求必有独立规划服务 |
| Controller | 跟踪目标并处理低层反馈 | 更低层控制指令 | 模型输出不一定是电机电流 |
| World model | 预测环境如何变化 | 未来图像、潜在状态、奖励等 | 不等于任意视频生成器或可靠物理模拟器 |

在“把桌上的杯子递给我”这个教学例子里：VLM 帮助识别目标、澄清“哪个杯子”；任务层选择“抓取 → 移近交接位置 → 等待接取”等子目标；VLA 生成相应的关节／末端目标与夹爪动作；controller 跟踪执行，再由新观察检查是否抓住或需要修正。真正交接还依赖具体系统的反馈与约束，例子不构成能力声明。

这些能力可以分模块，也可以合并，不要求固定串联三个独立模型。许多 VLA 以 VLM 为骨干：例如 [OpenVLA](https://openvla.github.io/)在视觉语言骨干上学习预测动作 token；[π0](https://www.pi.website/blog/pi0)加入通过 Flow Matching 生成连续动作的 action expert。视觉语言预训练提供语义基础，机器人数据与学习目标把这些表征接到动作；能理解目标并不自动带来精确控制或新场景泛化。

<a id="model-vs-algorithm"></a>
### 模型、学习算法和动作生成属于不同维度

| 维度 | 要问的问题 | 代表概念及其含义 |
|---|---|---|
| 功能与接口 | 模型理解什么、输出什么？ | VLM、特定语境的 VLT、VLA；分别从理解、任务决策与动作接口观察系统 |
| 网络结构 | 计算怎样组织？ | Transformer 等；同一种结构可承担不同功能 |
| 学习方式 | 用什么数据和目标改善行为？ | **BC（Behavior Cloning，行为克隆）**从示范学习动作；**RL（Reinforcement Learning，强化学习）**通过奖励与交互或离线经验改善策略 |
| 动作表示与生成 | 动作是什么、怎样算出来？ | 离散 token／连续数值；自回归、直接回归、Diffusion 或 Flow Matching；后两者也有各自训练目标 |
| 时间组织 | 一次预测和实际执行多少步？ | action chunk 一次预测多个时间步；预测长度与实际执行长度可以不同 |

这些维度可以组合。例如，VLA 可用 BC 从示范学习，再结合 RL 改进；BC 的监督也可采用动作分类、回归、去噪或 flow 目标。Diffusion / Flow Matching 不等于 RL，Transformer 也不等于 VLA。对 Infra 有用的是确认这些选择分别改变哪些数据字段、loss、计算步骤、状态和调度需求，具体机制见下文动作与学习章节。

## 2. MLLM：理解与交互为什么值得单独学习

当桌上有两个杯子时，“你指左边那个吗？”解决目标歧义；看到夹爪空着时，“没有抓住”帮助判定任务状态。模型即使不直接输出机械臂动作，也可能在澄清、任务分解和失败解释中有价值。

常见组织是视觉编码、模态连接与语言骨干，但并非所有模型结构相同，也不是每个模型都支持音频和长视频。自然语言中的“左边”还不足以确定机器人坐标系中的目标位姿；文本回答正确不能证明距离、遮挡或可达性正确。

对这类模型的工程验收先问：它看到哪些帧？能否说明不确定性？输出如何被下一层消费？用户中途更改目标时，旧计划和动作由谁失效？这是功能分解，并不要求每一项都由独立模型负责。

<a id="actions"></a>
## 3. VLA 与动作生成：一个 action 究竟是什么

教学例子中，action 可以写成“末端位置增量 + 旋转增量 + 夹爪目标”。也可以是绝对关节目标或其他表示。向量维数一样，仍可能因单位、坐标系、旋转表示、控制模式不同而完全不兼容。

纯教学例子：`a = [0.01, 0, -0.02, 0, 0, 0, 1]` 可约定为 robot-base 坐标下的 xyz 增量（米）、旋转向量增量（弧度）与夹爪目标（此例约定 1=闭合）。这不是任何框架的默认约定。若 H=4，则目标形状为 `[4, 7]`；episode 尾部仅两步有效时，mask 可为 `[1, 1, 0, 0]`。以动作回归为例，只在有效位置汇总误差；真实系统须核夹爪定义、旋转参数化和 loss 归一化方式。

一次预测 H 个动作步叫 action chunk。在同步 receding-horizon 教学例子中，执行前 K 步后根据新观察重规划，K 可小于 H；每步间隔为 Δt。相机可以持续采样，K 不表示暂停观察。ACT 的重叠预测和异步推理也不必遵循“等 K 步才开始下一次预测”。较长执行区间可能减少重算，却延迟把新观察用于修正。

<a id="action-compute"></a>
### 动作怎样生成，计算花在哪里

下表比较公开方法的计算路径，右栏是工程测量建议，不是跨模型性能排名。

| 代表来源 | 训练与推理路径 | Infra 需要核查什么 |
|---|---|---|
| [ACT](https://arxiv.org/abs/2304.13705v1) | 条件变分模型学习连续动作段，temporal ensembling 汇合同一时刻的多次预测 | 不应把 ACT 默认称为带语言条件的 VLA；也不能平均不同时刻的动作来替代它的融合 |
| [OpenVLA](https://arxiv.org/html/2406.09246v1#S3.SS2) | 训练：离散化动作，预测目标 token 的 cross-entropy；推理：按前面已生成的 token 自回归生成，再解码为动作 | token 之间的串行依赖、动作量化与反归一化；核前缀／KV 复用，不默认每个 token 都重新编码整张图 |
| [OpenVLA-OFT](https://arxiv.org/html/2502.19645v1#S4) | 训练：对连续动作段做 L1 回归；推理：并行解码，一次前向输出整段动作 | 去掉逐动作 token 生成循环后，仍要测图像／state 输入和 horizon 增加的计算、显存；更长 chunk 不是零成本 |
| [Diffusion Policy](https://arxiv.org/html/2303.04137v1#S2) | 训练：抽取噪声时刻，给示范动作加噪并学习预测噪声；推理：从噪声动作段开始迭代去噪，再执行其中一部分 | 去噪步数 `S`、sampler、条件编码复用和动作质量；`S` 是生成迭代次数，`H` 是动作步数，两者不同 |
| [π0](https://arxiv.org/html/2410.24164v4#S4) | 训练：在噪声与示范动作之间构造路径，学习速度场；推理：用 action expert 迭代积分得到连续动作段 | 核 observation prefix 的 KV 复用与 action suffix 重算范围；不能把每次积分都按完整 VLM 前向计费；此处核对论文 v4 方法说明 |

Diffusion 学去噪，Flow Matching 学连接分布的速度场；两者都可用于连续动作生成，但目标和采样过程不能直接视为相同。本文不以几句话替代完整推导，先能追踪输入→目标→生成→执行即可。

**训练计算与推理计算要分别画。** OpenVLA 训练可通过 teacher forcing（用右移的真值 token 作条件）并行计算目标位置；逐 token 串行依赖主要出现在生成时。上述 Diffusion / Flow Matching 训练抽取噪声或路径时刻构造监督，也不要求每个样本先跑完推理生成链再反传。推理采样步数增加，不应被机械换算成同比例的训练成本。

配置时先固定相机、历史帧、H、K、sampler 和精度，再分段测输入处理、条件编码、动作生成、通信与排队。减少生成步骤或使用量化，需要同时测时延分布与闭环质量。**动作步/s、每段生成延迟、实际执行时的观测年龄是三个不同指标**；只提高第一个，不能证明机器人更快响应环境变化。

## 4. 从数据到 loss：学的是哪种能力

给定观察历史、指令与本体状态，BC 从示范动作构造监督；离散 token 可用分类目标，连续动作可用回归、去噪或 flow 目标。目标不同，不代表一个必然优于另一个，须同时看数据、输出形式和闭环任务。

遥操作是一种示范采集方式，BC 是模仿学习方法，两者不是同一级分类。RL 依赖奖励与交互或离线经验；部署时重新规划不等于更新参数，也不是每个 VLA 都用 RL。

[π0.5](https://arxiv.org/abs/2504.16054v1)让异构数据与高层子任务监督成为阅读重点；[GR00T N1](https://arxiv.org/abs/2503.14734v1)连接视觉语言与动作模块；[SmolVLA](https://arxiv.org/abs/2506.01844v1)提供小型模型和异步执行路径的参考。阅读时分别画出“哪些样本监督哪些模块”，不要只记录模型名字。

训练配置先明确冻结哪些模块、哪些输入是必需的、动作在哪一步归一化、padding 是否参与 loss。视觉分辨率、历史帧数和 action horizon 都可能改变 activation 和 I/O；小动作头不意味着整体训练便宜。

<a id="sample-to-action"></a>
### 算一个样本：从 episode 到 loss，再到执行

以下全是教学假设，不对应某个框架的默认配置，也没有运行训练或机器人。选择一个用 **BC + 连续动作回归** 学习的策略，先固定它的数据契约：

| 字段 | 本例约定 | Infra 要保留的信息 |
|---|---|---|
| 任务与图像 | “把杯子递给我”；前视与腕部两路 RGB，经处理后为 `[2, 3, 224, 224]` | 相机顺序、真实采集时间、裁剪与处理版本；输入不能借用锚点之后的未来帧 |
| 本体状态 | 7 个关节角和 1 个夹爪开度，共 `[8]` | 关节名与顺序；角度用弧度、开度用米，各维含义与统计分别记录 |
| 动作 | `[Δx, Δy, Δz, Δrx, Δry, Δrz, g]`，7 维 | 此例位置增量用米、旋转向量增量用弧度，均约定在 robot-base 坐标表达；`g=1` 表示闭合，执行适配须遵守此约定 |
| 时间窗口 | 动作间隔 0.05 秒，一次预测 `H=4`，标签 shape 为 `[4, 7]` | 明确目标生效时刻、边界和有效 mask；这个 20 Hz 仅是例子中的动作步频，不是模型推理或低层控制频率 |

**第一步，取对窗口。** 沿用[纸面 E1](../../practice/experiments/embodied_contract_lab.md)的 episode A：动作时刻为 0.00、0.05、0.10、0.15 秒，0.15 是最后有效动作。本例把预测长度改成 4；锚点 0.10 秒对应动作标签时刻 `[0.10, 0.15, 0.20, 0.25]`，后两项不存在，mask 应为 `[1, 1, 0, 0]`。padding 不代表示范中的零动作，更不能接到 episode B。

**第二步，算清监督。** 动作按固定训练集统计归一化后得到 `y`，模型预测为 `ŷ`；本例用各维等权的 L1 回归。只对有效位置平均：

```text
loss = Σ[b,h] mask[b,h] × Σ[j=1..7] |ŷ[b,h,j] - y[b,h,j]|
       / (7 × Σ[b,h] mask[b,h])
```

若这个单样本两个有效动作步的逐维平均误差分别是 0.2、0.4，则 loss 为 `(0.2 + 0.4) / 2 = 0.3`；padding 的预测不贡献监督。实际方法可以有维度权重或独立夹爪目标，不必沿用此公式。全无有效动作的窗口应按约定拒收或跳过；分布式实现还要检查有效元素的全局归一化，不能默认各 rank 的有效数相同。

**第三步，更新并发布。** 反向传播和 optimizer 更新本次配置中可训练的参数；训练恢复需要模型、optimizer、sampler／RNG 等状态。部署包则绑定权重、processor、归一化统计、动作适配和机器人配置。换成动作 token、Diffusion 或 Flow Matching 时，监督目标与生成路径会变，但样本身份、时间和动作语义仍需一致。

**第四步，在线执行并回看结果。** 推理使用实时观察，没有示范动作标签，也不计算上述 BC loss。模型输出经反归一化和适配成为 controller 可消费的目标；可以预测 `H=4` 步，只执行前 `K=2` 步，再用新观察更新后续动作。这里的执行段只是同步教学方案，实际异步衔接需另定提交规则。

例如图像在 10.00 秒采集、相关动作在 10.05 秒执行，且两者使用同一时钟域，则执行时 observation age 是 50 ms。这只说明观测的新鲜度；是否可用仍取决于任务、动作目标时刻和控制约束。不能把动作在队列里滞留解释成模型的运动时间；详见[执行契约](embodied_infra.md#execution)。

<a id="bc-rl-infra"></a>
### BC、离线 RL、在线 RL：改变的是学习数据与反馈链

| 路径 | 从哪里学、优化什么 | 训练阶段的系统主链 | Infra 特别关注 |
|---|---|---|---|
| **BC** | 从示范的观察—动作关系学习模仿 | 已有示范 → 样本／batch → 监督 loss → 更新 | 示范覆盖、动作标注、采样混合与 I/O；一次参数更新不必等待机器人交互 |
| **离线 RL** | 从已有带奖励与状态转移等信息的数据优化策略，具体字段取决于算法 | 固定经验数据 → 策略／价值等算法所需更新 | 数据来源、奖励语义、动作覆盖与分布外动作估值；使用离线数据不等于 BC |
| **在线 RL** | 训练期间用策略与真实或模拟环境交互，将反馈用于后续更新 | policy → 环境 → 轨迹／reward → trainer → 新 policy | 环境与 reset 吞吐、轨迹完整性、终止／截断、采样策略版本和权重发布；异步时还需控制旧策略数据的使用 |

这些是学习方式的通用对照，具体 RL 算法可能增加 critic、replay buffer 或校正机制，不能把 LLM 的 token/logprob 接口直接当成所有连续动作策略的训练契约。已有的[RL 系统路线](../../04-rl-infra/roadmap.md)可复用身份、队列、版本与恢复思路，机器人环境接口需按具体算法另核。

BC 也需要闭环部署评估；部署时一边看、一边重新规划，并不意味着正在做 RL。只有执行经验进入相应训练目标并推动参数更新，才形成学习反馈。选择是否加入 RL，应先看当前失败来自数据覆盖、模型目标还是执行系统；这三个方向需要不同的修复。

<a id="world-model"></a>
## 5. World Model：预测未来与选择动作的区别

一个最小动作条件模型可以表示为：当前观察或潜在状态 + 候选动作 → 下一状态的预测。Policy 回答“做什么”，world model 回答“这样做可能发生什么”；具体系统可以把它用于候选比较、规划、想象训练或数据生成，也可以完全不用它。

视频生成质量只说明一部分问题。若换一个动作后预测几乎不变，或长期滚动违反接触／几何约束，就不能据画面逼真推断适合控制。策略也可能利用模型误差取得想象中的高分，真实环境却失败。

阅读这条主线时只抓四个边界：**是否以动作作为条件、预测什么、怎样用于控制或学习、用什么闭环证据验收**。具体验证的新模型与 benchmark 见[后续补扫](../../research/tracking/embodied_followup_2026-10-13.md)；架构披露与作者效果声明分开记录。

### 从基础模型继续读：三条机制演进

这些是已核原始方法的阅读判断，不是效果复现或对全部模型的分类。

| 学习问题 | 新证据 | 模型机制与系统后果 |
|---|---|---|
| 自己失败的经验怎么用？ | [RECAP](https://arxiv.org/abs/2511.14759v1) → [π0.7](https://arxiv.org/abs/2604.15483v1) | 由 advantage 条件到更丰富的策略上下文；工程推断：轨迹来源、质量条件与运行时控制模式要一起版本化 |
| 当前图像不够怎么办？ | [MEM](https://arxiv.org/abs/2603.03596v1) | 近期视觉与长期语义记忆承担不同职责；工程推断：episode 切换、失败恢复要管理记忆生命周期 |
| 世界预测能替代哪些评估？ | [DreamZero](https://arxiv.org/abs/2602.15922v1)、[MiraBench](https://arxiv.org/abs/2605.29360v1)、[OSCAR](https://arxiv.org/abs/2606.04463v1) | 联合视频与动作策略、动作条件可靠性基准、录制动作驱动视频是不同接口；不能仅凭 WAM 名称混同它们 |

发布机制与实现必须分层。例如 GR00T N1.7 的厂商文章可作为架构入口，但模型卡冲突字段仍需固定代码核对；接受一篇材料不等于接受其全部宣传结论。原始日期、作者与边界在[后续补扫](../../research/tracking/embodied_followup_2026-10-13.md)。

## 6. 从模型接到系统：配置与常见误判

<a id="infra-priorities"></a>
### Infra 岗位最核心的五个关注点

下面是本仓库对学习优先级的工程归纳；不同岗位的投入比例可不同，但都要能把性能指标接回数据和动作语义。

| 关注点 | 最少要理解什么 | 配置与验收时看什么 | 出问题时先查哪里 |
|---|---|---|---|
| **数据与动作正确** | 相机、state、action 的时间对齐；单位、坐标、控制模式、normalization、episode 边界与 mask | 回放样本，核原始帧、动作含义与反归一化；相同 shape 不等于相同语义 | [数据契约](embodied_data_io.md#sample-contract)；先查错位和动作约定，再判断模型能力 |
| **动作及时执行** | 采集→预处理→传输→推理→队列→控制器的完整路径；预测 H 步与执行 K 步的区别 | 端到端 p95/p99、observation age（执行时观测已过去多久）、deadline miss；迟到响应与旧动作失效规则 | [三种时间与提交边界](embodied_infra.md#execution)；检查旧画面、排队和已提交动作 |
| **训练资源有效利用** | 视频解码、时序采样、H2D、计算和通信；哪些模块训练／冻结，哪些状态占显存 | 有效样本吞吐、阶段耗时、显存与慢 rank；在线 RL 还需环境采样、reward、轨迹与权重版本管理 | [I/O 流水线](embodied_data_io.md#pipeline) → [训练阶段](../roadmap.md#stage-4)；测量后再决定预取、batch 或分片 |
| **发布与恢复一致** | 模型、processor、norm stats、action adapter、robot profile 的成套版本；训练与执行状态的区别 | 训练恢复核 sampler／RNG 等；执行恢复核 episode、记忆、队列与动作有效期，旧动作不能盲目重放 | [部署契约](embodied_data_io.md#deployment)与[系统平台章](agentic_for_embodied.md)；先查版本和状态归属 |
| **闭环评估可信** | 离线 loss、仿真任务与真机任务的不同证据；泛化到底改变了什么 | 固定任务分布、失败分母、人工介入和 reset 协议；性能优化前后同时检查任务成功率 | [评估边界](embodied_infra.md#evaluation)；区分模型、数据、时延、控制接口和评估分布变化 |

VLM 工作负载先看视觉输入与上下文成本；任务层先看子目标接口、完成判定和中途改目标如何取消旧计划；VLA 工作负载先看动作表示、生成步骤与执行时限。这是按职责分解的工程检查法，不能从一个缩写推断固定部署架构。

### 常见现象：先定位失败在哪个边界

下面是排查假设，不是仅凭现象就能确定的根因。

| 现象与常见误判 | 第一批证据 | 怎样进一步区分 |
|---|---|---|
| 同一机器人换 checkpoint 后，抓取位置系统性偏移；认为“模型退化” | 同一帧与 state 下的原始输出、反归一化结果、processor／stats／adapter／robot profile 版本 | 若数值还原或坐标变换已错，先修契约；契约一致后再评估模型变化 |
| GPU 推理更快，机器人却更常抓空；认为“吞吐提升就会更可靠” | 从采集到执行的时间线、队列、H／K 与旧响应处理 | 分清 forward 加速与端到端观测变旧；再查采样步数或量化是否改变动作质量 |
| 离线 loss 很低，新场景却失败；认为“数据管线已证明正确” | 原始 episode 回放、mask、训练／验证分组、闭环失败轨迹 | 排错位和相邻窗口泄漏；若都正常，再检查未覆盖的场景及执行误差累积 |
| 某模型宣称泛化提高；认为“所有新任务都会更好” | 新物体、背景、指令、任务组合、本体分别怎样变化；训练重叠与人工介入 | 在相同任务和成功定义下比较，不能把单个泛化维度推广到全部维度 |
| 权重可下载，训练却无法复现；认为“公开 checkpoint 等于完整开放” | 数据、训练配方、依赖、动作约定与评估协议 | 分开验证能否加载、能否推理、能否重训及能否重现闭环结果 |

排查顺序通常先接口与数据，再生成与调度，最后才归因更复杂的模型机制；这是工程建议，具体故障应由测量决定。下一步读[数据与 I/O](embodied_data_io.md)，再复用[训练路线](../roadmap.md#stage-4)和[系统平台章](agentic_for_embodied.md)。

## 7. 第一轮讨论与掌握检查

最小学习产出是一页路径：**一条机器人轨迹 → 一个训练样本 → loss → 参数更新 → 推理动作 → controller 执行 → 任务结果**。标出每个边界的数据、时间、版本和验收指标；这比只记住模型名称更能帮助定位 Infra 问题。

试着只用一张纸说明：观察包含什么？action 的单位和坐标是什么？H 与 K 各多长？loss 学什么？哪部分参数被更新？任务成功如何定义？如果这些问题答不清，先不比较模型榜单。

我们可以从“杯子在动作执行到一半时被人移动”讨论：模型需要更大的参数量、更快推理、更短执行段，还是新的观察？答案取决于失效的位置，不能预先只选一种优化。

可先自查三个问题，再回看对应正文：

1. 预测四步、执行两步，就是 RL 吗？——不是；这描述执行与重规划，是否 RL 要看训练数据、奖励目标与参数更新。
2. 有效动作步数不同的 batch，可以一律除以固定 `batch × H × D` 吗？——不能据此得到上例的有效元素平均；padding 比例会改变 loss 的尺度，须核实际目标和全局归一化。
3. 动作头小，是否意味着整次推理便宜？——还要计入图像处理、视觉语言骨干、动作生成迭代、数据传输和排队；先测完整路径。
