### Understood

- Asynchronous RL 的主要性能收益来自 rollout 与 training 的流水线重叠；staleness 是允许重叠时的正确性预算，而不是加速机制本身。
- `staleness = 0` 对应严格使用最新 policy 的 on-policy 数据。放宽 staleness 可以减少等待，但会增加 behavior policy 与 current policy 的偏移，过旧样本可能造成 importance ratio 异常、clipping 增多和有效样本率下降。
- Structural bubble 来自固定 rollout/training GPU 分区造成的长期速率失配；residual bubble 来自 response-length 动态、模型并行粒度、staleness 和运行时阶段边界。
- BiDiRL 借用的是 GPU 的执行角色，不是把单个算子或单条 decode 拆到另一侧。借用以兼容的完整 model replica 为粒度，并受 static planner 预先构造的 resource envelope 约束。
- `Rollouter-on-TrainPoll` 使用空闲 training GPU 执行额外的 prompt-level rollout group；`Trainer-on-RollPoll` 使用空闲 rollout GPU 执行 training chunk。
- BiDiRL 可以提高 GRPO rollout group 的总体生产能力，但不能消除同一 group 中最后一个超长 response 带来的完成 barrier。解决组内长尾还需要 response-level scheduling、preemption/resume 或算法层改造。
- 论文的 RL training throughput 定义为 measured training steps 消费的 prompt 与 response token 总数除以端到端 step wall time。它不是单独的 decode throughput、MFU、P99 latency 或 time-to-quality。
- Figure 5 证明 BiDiRL 在多种配置下具有端到端吞吐优势，但跨框架比较会混入实现差异；Figure 6 的同代码消融更能说明双向借用和 model-guided admission 的独立贡献。

### Verified Facts

- BiDiRL 原型基于 veRL 扩展约 8.3K 行 Python，使用 vLLM 执行 rollout、PyTorch FSDP 执行 training、Ray 负责 orchestration。
- AReaL 是外部性能基线，不是 BiDiRL 的实现底座；论文没有证明 BiDiRL 可以直接接入 AReaL。
- 截至 2026-07-14，论文和 arXiv 页面没有提供可验证的官方代码仓库。
- Hot switch 并非零成本。论文在 2B/4B 设置下报告数秒级 state movement 与 synchronization 开销，因此短暂 idle window 不一定值得借用。

### Questions

- Partial rollout 在跨 worker 恢复时具体保存哪些状态：generated prefix、KV cache、sampling RNG state 和 per-response metadata 分别如何处理？
- 完整 policy state、optimizer state 与 communicator 生命周期在故障或抢占场景下如何保证一致？
- 论文只验证 2B-8B 模型和 1K-4K response；扩展到更大模型、长上下文和多节点 TP/PP 后，hot-switch 成本是否仍能被摊薄？
- Figure 8 只展示前 60 个训练 step，是否足以支持“不影响完整收敛”的结论？
- 如果迁移到 AReaL 或其他异步 RL 框架，需要改造哪些 worker lifecycle、state sync 和 scheduler 接口？
